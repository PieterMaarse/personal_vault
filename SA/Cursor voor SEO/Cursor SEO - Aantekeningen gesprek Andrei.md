## Samenvatting

Naar de mening van Andrei is het grootste risico dat er fouten in de code komen en dat dit dan wordt verkocht aan de klant. Dit is iets om heel goed op te letten en daarom is het erg belangrijk dat mensen begrijpen wat er in hun code gebeurt. Vooral bij grotere projecten zal cursor meer fouten maken.

Echter, als cursor tijd zou besparen, dan kan deze extra tijd ook worden geïnvesteerd in het checken van andermans code (wat naar zijn mening te weinig gebeurt). Ook kan cursor juist goed worden gebruikt voor het refactoren (herstructureren) van code, waardoor de code beter kan worden.

De privacy kant maakt Andrei zich wat minder zorgen om, maar voor SEO is dit wel een grote overweging. Wel moet overwogen worden hoe betrouwbaar we het vinden dat de privacy-beschermende maatregelen daadwerkelijk worden nageleefd.

Andrei's voorstel is om een pilot te doen, waarbij 2 vragen gesteld worden:
1. Wat is de tijdsbesparing
2. Hoeveel fouten maakt Cursor

Zelf zou ik daar nog aan toevoegen:
3. Hoeveel van de resulterende code begrijp je?


## Aantekeningen

- Pilot doen
- risico bij fouten doorverkopen naar de klant
- Als het genoeg tijd bespaart kun je die tijd gebruiken om feedback op elkaars code te geven, wat nu te weinig is.
- Ligt eraan hoe groot het product is, bij grotere werkt ie minder
- Feedback vragen aan mensen
- Kan ook goed zijn om code te restructuren en vragen te stellen
- 3 vragen:
	- Wat is de tijdsbesparing?
	- Hoe veel fouten maakt ie / hoe betrouwbaar is het?
	- Begrijp je zelf de code nog?
- Qua privacy kan verschillen wat de regels zijn en wat in de praktijk gebeurt
